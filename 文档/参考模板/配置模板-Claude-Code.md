## 2. 快速开始

### 2.1 一键初始化脚本

创建 `scripts/init-claude-config.sh`：

```bash
#!/bin/bash
# 初始化 Claude Code 配置

# 创建目录结构
mkdir -p .claude/{agents,rules,skills,commands,hooks}
mkdir -p 文档/{核心文档,夜间日志}

# 创建 .gitignore
cat >> .gitignore << 'EOF'
# Claude Code
.claude/settings.local.json
.claude/state.json
EOF

echo "Claude Code 目录结构创建完成！"
echo "接下来请复制配置文件到对应目录"
```

### 2.2 配置优先级

从高到低：
1. CLI 参数
2. `.claude/settings.local.json`（个人）
3. `.claude/settings.json`（团队）
4. `~/.claude/settings.json`（用户全局）

## 3. CLAUDE.md 模板

> **位置：** 项目根目录 `/CLAUDE.md`

```markdown
# CLAUDE.md · AI 开发规范

> 本文档适用于所有在本项目工作的 AI 助手

---

## 1. 核心工作模式

### PM 的工作方式
PM 只用中文描述需求，不需要记任何命令。AI 自动判断该做什么。

**PM 只需要：**
- 用中文说想要什么功能
- 用中文描述遇到的问题
- 最后看网页确认结果

**AI 自动完成：**
- 分析需求，判断是开发/修复/测试
- 执行所有技术操作
- 验收前自己确认功能可用

### 自动执行原则
- ✅ 读取文件 → 直接读，不问
- ✅ 编辑代码 → 直接改，不问
- ✅ 运行测试 → 直接跑，不问
- ✅ 启动服务 → 直接启动，不问
- ✅ 修复报错 → 直接修，不问
- ❌ 删除重要文件 → 必须问
- ❌ 修改 .env → 必须问
- ❌ git push → 必须问

---

## 2. 验收前必须完成

在告诉 PM "打开网页验收" 之前，AI 必须自己完成：

1. **确认服务运行中** - `docker compose ps`
2. **确认代码无报错** - `pnpm build` 或 `npx tsc --noEmit`
3. **确认接口可访问** - `curl http://localhost:xxxx/api/health`
4. **确认页面可打开** - 前端服务在运行

**只有以上全部通过，才能告诉 PM 去看网页。**

---

## 3. 输出格式

任务完成后，必须输出：

```
## 任务完成

### 做了什么
- [具体改动1]
- [具体改动2]

### 已验证
- ✅ 服务运行中
- ✅ 代码无报错
- ✅ 接口可访问

### 验收方式
打开网页：http://localhost:xxxx/xxx
应该看到：[具体描述]
```

## 4. 技术栈约束

> 根据项目实际情况修改

| 类别 | 技术选型 |
|------|---------|
| 语言 | TypeScript |
| 后端 | NestJS / Express / ... |
| 前端 | Next.js / React / Vue / ... |
| 包管理 | pnpm / npm / yarn |
| 数据库 | PostgreSQL / MySQL / ... |
| 缓存 | Redis |
| 容器化 | Docker Compose |

**禁止随意引入：**
- 未经批准的新框架
- Beta / Alpha 版本依赖
- 微服务架构（V1 阶段）

---

## 5. 6 段固定结构

每轮开发回复必须包含：

1. **本轮任务理解（≤5行）** - 只做什么/不做什么
2. **变更计划 & 文件列表** - 允许改动的白名单
3. **实现内容（按文件分段）** - 具体代码改动
4. **验证步骤** - 执行目录 + 命令 + 预期输出
5. **风险点 & 自检清单** - 影响范围 + 潜在风险
6. **回滚方案** - 如何撤销本次变更

---

## 6. 禁止事项

- ❌ 顺手优化 / 顺手重构
- ❌ 跨模块改动（单任务只动一个模块）
- ❌ 默认追新（禁止安装最新版依赖）
- ❌ 硬编码密钥或敏感信息
- ❌ 不提供回滚方案的修改
- ❌ 写死本机绝对路径（如 C:\Users\...、/Users/...）

---

## 7. 时间盒与小步提交

### 时间盒（强制）
- 单任务时间盒：30-60 分钟
- 超时必须停止，输出：当前进度 + 卡点 + 下一步建议

### 小步提交（强制）
- 单次提交建议 ≤ 5 个文件
- 每个变更配：自检清单 + 验收步骤 + 回滚步骤

---

## 8. 成本与配额护栏

任何第三方 API / 模型调用 / 链上 RPC / 付费服务，必须写清：
- 配额限制
- 失败策略
- 预估调用量与成本上限
- 达到上限时的降级策略（缓存/降频/只读模式）

---

## 9. AI 幻觉防护

### 来源标注（强制）
任何新增调用（库/方法/API）必须标注：
- 来自哪个包/模块
- 是否需要安装/启用
- 若第三方 API：需要哪些配置项 + 失败兜底

### 先列清单再写代码
对复杂功能：先输出"将要新增的函数/模块/文件清单"再写代码，防止凭空捏造方法名。

---

## 10. 测试用例最小集

每个原子任务至少提供 3 条测试用例：

| 类型 | 说明 |
|-----|------|
| 正常路径 | 成功场景 |
| 异常路径 | 输入非法/权限不足/依赖失败 |
| 边界路径 | 空值/极值/超时/特殊字符 |

涉及资金/结算/计费：必须补充对账/验算脚本。

---

## 11. 修复前必须全局理解

修复任何 bug 前，必须先做：

1. **理解问题根源** - 不只看报错，要理解为什么
2. **分析影响范围** - 这个模块被谁调用？
3. **检查相关代码** - 读取相关文件，理解整体逻辑
4. **制定最小修复方案** - 改动越少，风险越小

---

## 12. 可恢复性优先

- 任一步骤失败，都要保证可以回退到上一个"已知可运行版本"
- 用户端尽量不中断（尤其资金、支付、登录、关键业务）
- 关键错误日志可定位（含 request_id / trace_id）
- 关键配置通过环境变量管理（禁止硬编码密钥）
- 失败有明确兜底（超时/重试/错误提示/降级）

---

## 13. 夜间工作模式

触发词：
- "今晚帮我做..."
- "夜间任务..."
- "明早验收..."

规则：
- 一口气做完所有任务
- 遇到问题自己解决或跳过
- 生成日志到 `文档/夜间日志/`
- 禁止架构变更、引入新依赖

---

## 版本记录

| 版本 | 日期 | 变更说明 |
|-----|------|---------|
| v1.0 | YYYY-MM-DD | 初始版本 |
```

## 6. Rules 规则文件

### 6.1 开发工作流

> **位置：** `.claude/rules/dev-workflow.md`

```markdown
# 开发工作流规则（强制执行）

## 6 段固定结构（每轮必须输出）

1. **本轮任务理解（≤5行）** - 只做什么 / 不做什么
2. **变更计划 & 文件列表** - 白名单 + 禁止项
3. **实现内容（按文件分段）** - 补丁风格说明
4. **验证步骤** - 目录 + 命令 + 预期输出
5. **风险点 & 自检清单** - 影响 + 风险 + 回滚方式
6. **回滚方案** - 具体步骤
```

## 9. Hooks 钩子脚本

### 9.1 敏感文件保护

> **位置：** `.claude/hooks/protect-sensitive.sh`

```bash
#!/bin/bash
# Hook: 保护敏感文件
# 触发时机: PreToolUse (Edit|Write)

input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // empty')

if [[ -z "$file_path" ]]; then
  exit 0
fi

# 敏感文件模式
sensitive_patterns=(
  ".env"
  ".env.local"
  ".env.production"
  "secrets"
  "credentials"
  ".pem"
  ".key"
)

for pattern in "${sensitive_patterns[@]}"; do
  if [[ "$file_path" == *"$pattern"* ]]; then
    echo "BLOCKED: Cannot edit sensitive file: $file_path" >&2
    exit 2  # 返回 2 表示阻止操作
  fi
done

exit 0
```

### 9.2 变更日志记录

> **位置：** `.claude/hooks/log-changes.sh`

```bash
#!/bin/bash
# Hook: 记录代码变更日志
# 触发时机: PostToolUse (Edit|Write)

LOG_DIR="$HOME/.claude/logs"
LOG_FILE="$LOG_DIR/changes-$(date +%Y%m%d).log"

mkdir -p "$LOG_DIR"

input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // empty')
tool_name=$(echo "$input" | jq -r '.tool_name // empty')

if [[ -n "$file_path" ]]; then
  echo "[$(date '+%Y-%m-%d %H:%M:%S')] $tool_name: $file_path" >> "$LOG_FILE"
fi

exit 0
```

```markdown
## 1. 协作核心原则

### 1.1 决策权划分

| 决策类型 | 负责方 | 说明 |
|---------|-------|------|
| 功能需求 | PM | 做什么、不做什么、验收标准 |
| 技术实现 | AI | 怎么做、用什么库、代码怎么写 |
| 架构选型 | PM + AI | AI 提供方案,PM 最终决策 |
| Bug 修复 | AI | AI 负责定位和修复,PM 负责验收 |

**核心规则**:
- PM 只做「通过/打回」,不写代码
- AI 提供完整实现,不做口头承诺
- 有歧义时 AI 先提供 2-3 种方案,PM 选择后再实现

### 1.2 验收标准(Definition of Done)

一次交付完成,必须同时满足:

1. **可用能力**: 本轮只交付 1 个原子任务(一个接口/脚本/页面)
2. **肉眼可见成功信号**: 必须能用 `curl/Postman/脚本/页面` 证明功能已生效
3. **验收步骤**: 提供明确的执行步骤 + 预期结果
4. **回滚方案**: 明确如何撤销本次改动
5. **风险与影响说明**: 说明潜在风险点、影响范围

不满足以上任意一条:**一律视为"未完成",必须打回**。

导致:
- 维护成本爆炸

| 依赖版本 | 禁止默认追新,优先稳定版 |

**例外情况**:
- 只有在 PM 明确要求"用新技术/尝鲜"时,才允许引入新框架/新范式/冷门依赖
```

```
- 前后端一起大改
- 同时重构目录结构 + 改业务逻辑

### 4.3 提交规范

**小步提交**:
- 单次提交建议 ≤ 5 个文件
```

```
## 8. 常见问题 FAQ

### Q2: PM 提的需求不清晰怎么办?

**答**: 先澄清需求,确认边界,再给计划。

**示例**:
```
您说的"优化性能",具体指:

3. 前端加载速度优化?

## 15. 夜间自动开发模式安全护栏（完整版）

> **适用场景：** PM 希望利用夜间睡眠时间让 AI 自动执行开发任务

### 15.1 权限边界与角色限制

**夜间模式下的角色限制：**
- 只允许 task-executor 角色执行任务
- 严禁修改架构、重构代码或调整技术选型
- 所有任务必须是 PM 白天已明确批准的 checklist 条目

**工具与命令限制：**
- 允许：Read、Write、Edit、Glob、Grep、Bash（测试/构建）
- **严禁：** AskUserQuestion、EnterPlanMode 等交互工具
- **严禁：** rm -rf、DROP DATABASE、docker compose down -v 等破坏性命令

### 15.2 代码修改范围限制

**单次任务限制：**
- 一次只完成 1 个原子任务
- 禁止跨模块修改
- 禁止"顺手优化"

**代码量限制：**
- 单次修改文件数 ≤ 5 个
- 单个文件修改行数建议 ≤ 200 行
- 超限需标记为"超限任务"，等待晨间审核

### 15.3 Git 分支与提交策略

**专用夜间分支：**
- 分支格式：`night-run/<task-id>-<date>`
- **严禁直接提交到：** main、dev、staging、production
- **严禁执行：** git push --force、git rebase、git reset --hard

**原子提交：**
- 每完成一个子步骤提交一次
- Commit message 格式：`[Night-Run] <task-id> - <简短描述>`

### 15.4 测试与验证要求

**强制测试：**
1. 编译检查：`pnpm build` 或 `tsc --noEmit`
2. 代码规范：`pnpm lint`
3. 单元测试：相关模块测试
4. 集成测试：API 接口验证
5. 回归测试：冒烟测试清单

**验证失败策略：**
- 立即停止后续操作
- 在夜间日志中详细记录失败信息
- 标记任务状态为 `FAILED`，等待 PM 晨间介入

### 15.5 资源与成本限制

**计算资源限制：**
- 单任务执行时间 ≤ 2 小时
- 超时自动中止，标记为 `TIMEOUT`

**迭代次数限制：**
- 单任务"尝试-失败-修复"循环 ≤ 3 次
- 超过进入"反死循环模式"，标记为 `STUCK`

**外部服务限制：**
- 禁止调用付费第三方 API（除非已设置配额）
- 禁止访问生产环境
- 禁止发送真实邮件/短信/Push

### 15.6 环境隔离与数据安全

**环境限制：**
- 只允许在 dev 或 staging 环境
- **严禁操作 production**

**数据操作限制：**
- 禁止 DELETE、TRUNCATE、DROP
- 修改数据必须先备份 + 提供回滚脚本

**隐私保护：**
- 禁止在日志中输出密钥、Token、密码
- 禁止修改鉴权/加密相关代码（除非明确任务目标）

### 15.7 日志与晨间审核

**夜间日志必须包含：**

```markdown
# 夜间开发报告 - [任务简述]

**执行日期**: YYYY-MM-DD
**任务状态**: SUCCESS / FAILED / TIMEOUT / STUCK

## 1. 任务概述
- 任务 ID：
- 开始/结束时间：

## 2. 执行摘要
- 修改的文件列表
- 执行的测试结果

## 3. 验证结果
- 编译：✅/❌
- Lint：✅/❌
- 测试：X passed / X failed

## 4. 问题与风险
- 遇到的问题
- 需要 PM 关注的事项

## 5. 晨间验收清单
- [ ] 验收步骤1
- [ ] 验收步骤2
- 如何合并：`git merge ...`
- 如何回滚：`git revert ...`
```

**晨间审核流程：**
1. 查看 `文档/夜间日志/<date>-<task-id>.md`
2. 检查任务状态
3. 执行验收清单
4. 合并或回滚

## 16. 完整行为规范清单（25 条）

24. **文档即代码** - 配置变更必须同步更新文档
