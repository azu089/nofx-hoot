# HOOT 灾难恢复文档

> 版本: v1.0
> 更新日期: 2026-02-06

---

## 1. 概述

本文档描述 HOOT 平台在发生灾难性故障时的恢复流程，包括数据库崩溃、服务器损坏、数据丢失等场景。

### 1.1 恢复时间目标 (RTO)

| 故障类型 | 目标恢复时间 |
|---------|-------------|
| 单个服务崩溃 | < 5 分钟 |
| 数据库故障 | < 30 分钟 |
| 服务器损坏 | < 2 小时 |
| 完全灾难恢复 | < 4 小时 |

### 1.2 恢复点目标 (RPO)

| 数据类型 | 最大数据丢失 |
|---------|-------------|
| 用户数据 | < 24 小时 |
| 交易记录 | < 1 小时 |
| 配置数据 | 0（实时备份） |

## 2. 备份策略

### 2.1 自动备份

```bash
# 每日 3:00 自动备份
0 3 * * * /opt/hoot/scripts/backup.sh --upload-s3

# 每 5 分钟监控检查
*/5 * * * * /opt/hoot/scripts/monitor.sh --alert
```

### 2.2 备份位置

| 备份类型 | 本地路径 | 远程位置 |
|---------|---------|---------|
| 数据库 | /var/backups/hoot/ | s3://hoot-backups/database/ |
| 配置文件 | /opt/hoot/.env | s3://hoot-backups/config/ |
| 日志 | /var/log/hoot/ | s3://hoot-backups/logs/ |

### 2.3 手动备份

```bash
# 立即执行备份
cd /opt/hoot
./scripts/backup.sh --upload-s3

# 验证备份
ls -la /var/backups/hoot/
aws s3 ls s3://hoot-backups/database/
```

## 3. 恢复流程

### 3.1 单个服务崩溃

**症状**: 某个 Docker 容器停止运行

**恢复步骤**:

```bash
# 1. 检查容器状态
docker ps -a | grep hoot

# 2. 查看日志
docker logs hoot-api --tail 100

# 3. 重启容器
docker restart hoot-api

# 4. 验证恢复
curl http://localhost:4001/api/health
```

### 3.2 数据库故障

**症状**: PostgreSQL 无法连接或数据损坏

**恢复步骤**:

```bash
# 1. 停止所有服务
docker compose down

# 2. 找到最近的备份
ls -la /var/backups/hoot/ | tail -5
# 或从 S3
aws s3 ls s3://hoot-backups/database/ --human-readable | tail -5

# 3. 下载备份（如果需要）
aws s3 cp s3://hoot-backups/database/hoot_db_20260206_030000.sql.gz /tmp/

# 4. 删除旧数据卷（危险操作，确保有备份！）
docker volume rm hoot_postgres_data

# 5. 启动数据库容器
docker compose up -d postgres

# 6. 等待数据库就绪
sleep 10

# 7. 恢复数据
gunzip -c /var/backups/hoot/hoot_db_20260206_030000.sql.gz | \
  docker exec -i hoot-postgres psql -U hoot -d hoot

# 8. 启动其他服务
docker compose up -d

# 9. 验证恢复
./scripts/monitor.sh
```

### 3.3 服务器损坏

**症状**: 整台服务器无法访问

**恢复步骤**:

```bash
# 1. 在新服务器上准备环境
# 安装 Docker
curl -fsSL https://get.docker.com | sh
apt install -y docker-compose-plugin awscli

# 2. 克隆代码
git clone https://github.com/your-org/hoot.git /opt/hoot
cd /opt/hoot

# 3. 恢复配置文件
aws s3 cp s3://hoot-backups/config/.env .env

# 4. 下载最新数据库备份
aws s3 cp s3://hoot-backups/database/$(aws s3 ls s3://hoot-backups/database/ | sort | tail -1 | awk '{print $4}') /tmp/backup.sql.gz

# 5. 启动基础设施
docker compose up -d postgres redis

# 6. 等待数据库就绪
sleep 15

# 7. 恢复数据
gunzip -c /tmp/backup.sql.gz | docker exec -i hoot-postgres psql -U hoot -d hoot

# 8. 启动所有服务
docker compose up -d

# 9. 配置 Nginx/SSL（如果需要）
# ...

# 10. 更新 DNS 指向新服务器
# ...

# 11. 验证所有服务
./scripts/monitor.sh
```

### 3.4 Redis 数据丢失

**症状**: Redis 缓存丢失，用户需要重新登录

**恢复步骤**:

```bash
# Redis 数据通常可以重建，不需要特殊恢复
# 1. 重启 Redis
docker restart hoot-redis

# 2. 清除可能的损坏数据
docker exec hoot-redis redis-cli FLUSHALL

# 3. 用户需要重新登录（JWT 缓存丢失）
```

## 5. 预防措施

### 5.1 定期检查

```bash
# 每周手动执行
# 1. 验证备份完整性
gunzip -t /var/backups/hoot/hoot_db_*.sql.gz

# 2. 检查 S3 备份
aws s3 ls s3://hoot-backups/database/ --summarize

# 3. 测试恢复流程（在测试环境）
```

### 5.2 监控告警

确保以下告警已配置:

- [ ] API 服务不可用
- [ ] 数据库连接失败
- [ ] Redis 连接失败
- [ ] 磁盘使用率 > 80%
- [ ] 内存使用率 > 80%
- [ ] 备份失败

### 5.3 定时任务配置

```bash
# 查看当前定时任务
crontab -l

# 添加定时任务
crontab -e

# 内容:
# 每日 3 点备份
0 3 * * * /opt/hoot/scripts/backup.sh --upload-s3 >> /var/log/hoot/backup.log 2>&1

# 每 5 分钟监控
*/5 * * * * /opt/hoot/scripts/monitor.sh --alert >> /var/log/hoot/monitor.log 2>&1

# 每周清理日志
0 4 * * 0 find /var/log/hoot -name "*.log" -mtime +30 -delete
```

## 6. 回滚指南

### 6.1 代码回滚

```bash
# 1. 查看最近的提交
git log --oneline -10

# 2. 回滚到指定版本
git checkout <commit-hash>

# 3. 重新构建并部署
docker compose build
docker compose up -d
```

### 6.2 数据库回滚

```bash
# 1. 停止服务
docker compose stop api web telegram-bot

# 2. 备份当前数据（以防万一）
./scripts/backup.sh

# 3. 恢复到指定时间点的备份
gunzip -c /var/backups/hoot/hoot_db_YYYYMMDD_HHMMSS.sql.gz | \
  docker exec -i hoot-postgres psql -U hoot -d hoot

# 4. 重启服务
docker compose up -d
```
