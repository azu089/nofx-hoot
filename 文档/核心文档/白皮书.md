## 摘要（Executive Summary）

HOOT 是一个面向全球加密货币投资者的 **AI 量化交易即服务（QaaS）** 平台。平台将华尔街级别的量化交易能力封装为一键订阅的 SaaS 产品，用户无需编程技能、无需自建服务器、无需理解复杂的技术指标，只需绑定交易所 API Key 并选择策略，即可享受 7x24 小时全自动量化交易服务。

HOOT 采用独创的 **中央信号引擎架构**，一台 Freqtrade 信号引擎通过 BullMQ 消息队列将交易信号按订阅维度分发给所有用户，再由 CCXT 统一接口在各用户的交易所账户上执行实盘交易。相比传统的"一用户一服务器"架构，基础设施成本降低 96%，同时实现理论上无上限的用户扩展能力。

**核心数据亮点：**

| 指标 | 数值 | 说明 |
|------|------|------|
| API 端点 | **275+** | 覆盖用户端、管理端、代理商端全业务 |
| 数据库表 | **53** | PostgreSQL 全关系型设计，Prisma ORM 类型安全 |
| 前端页面 | **28** | 用户端 + 管理端全覆盖 |
| 移动端组件 | **29** | 原生级移动端体验 |
| 支持语言 | **10** | 中文简繁、英、日、韩、越、泰、印尼、俄、土耳其 |
| 风控机制 | **8 大** | 止盈止损、追踪止损、黑天鹅保护、熔断器等 |
| 资金精度 | **Decimal(18,8)** | 全平台 decimal.js 精确计算，杜绝浮点误差 |
| 支持交易所 | **Binance / OKX / Bybit** | 通过 CCXT 统一接口，可快速扩展至 100+ |

## 1. 愿景与使命

### 1.1 行业痛点

加密货币市场 7x24 小时不间断运行，蕴含巨大机会，但普通投资者面临三大门槛：

#### 门槛一：技术壁垒高

| 传统量化交易要求 | 说明 | 门槛等级 |
|-----------------|------|---------|
| 编程能力 | 需掌握 Python/C++，编写策略代码 | 极高 |
| 数学/统计学 | 理解均值回归、动量因子、协整检验等 | 高 |
| 服务器运维 | 搭建 VPS、配置 Docker、保持 24 小时运行 | 中高 |
| 交易所 API 对接 | 理解 REST/WebSocket 协议、处理限流与异常 | 中高 |
| 回测与优化 | 下载历史数据、避免过拟合、参数寻优 | 高 |

**现实情况**：全球加密货币持有者超过 5 亿人，但具备量化交易能力的不足 1%。大量投资者依赖手动交易、社群消息或情绪判断，长期来看胜率极低。

#### 门槛二：资金成本高

| 成本项 | 传统自建量化 | HOOT 方案 |
|--------|-------------|-----------|
| 服务器（VPS） | $12-50/月/策略 | $0（平台统一运行） |
| 数据服务 | $50-200/月 | $0（平台统一采集） |
| 策略研发 | 数月~数年人力 | $0（现成策略库） |
| 监控运维 | 需 7x24 值守 | $0（全自动监控） |
| 回测工具 | $0-500/月 | $0（内置回测） |
| **总计** | **$100-750+/月** | **$15-99/月（会员费）** |

#### 门槛三：信任缺失

加密货币行业信任事件频发，用户对"将资金交给第三方"存在天然顾虑：

- **交易所暴雷**：FTX、Mt.Gox 等事件导致用户资金灭失
- **跑路项目**：大量量化交易项目以"高收益"为噱头圈钱跑路
- **黑箱操作**：用户无法看到策略逻辑与执行细节
- **数据造假**：回测曲线可以伪造，实盘收益无法验证

**HOOT 的信任解决方案：**

| 痛点 | HOOT 的解决方式 |
|------|----------------|
| 资金安全 | 用户资金始终在自己的交易所账户，HOOT 无权提现 |
| 策略透明 | 每笔交易实时推送，用户可随时查看持仓与收益 |
| API Key 安全 | AES-256-GCM 加密存储，仅交易时内存解密 |
| 代码开源 | 核心代码 GitHub 开源，接受社区审计 |
| 盈利共享 | 仅在用户盈利时收取燃油费，利益深度绑定 |

### 1.2 HOOT 解决方案：QaaS（量化即服务）

**QaaS（Quantitative as a Service）** 是 HOOT 的核心商业模式定义。类似于 SaaS 将软件服务化，QaaS 将量化交易能力服务化：

```
传统模式:
  投资者 → 自学编程 → 自建策略 → 自租服务器 → 自己运维 → 交易
  (耗时数月，成本高昂，成功率低)

HOOT QaaS 模式:
  投资者 → 注册 → 绑定交易所 → 选择策略 → 自动交易
  (5 分钟上手，$15/月起步，专业级策略)
```

**QaaS 的核心价值主张：**

1. **技术民主化**：将专业量化算法包装为"一键订阅"产品，消除技术门槛
2. **成本平民化**：中央引擎架构实现规模效应，100 用户共享 1 台引擎，成本降低 96%
3. **资金自主权**：用户资金始终在自己的交易所账户，HOOT 仅通过 API 发送交易指令
4. **透明可追溯**：每笔信号生成、分发、执行全链路可追溯，附带 request_id 审计

### 2.2 中心化信号引擎

HOOT 的核心技术创新在于 **中央信号引擎架构**——与传统"每用户部署独立策略引擎"不同，HOOT 仅运行一台 Freqtrade 实例，通过 BullMQ 消息队列将交易信号分发给所有订阅用户。

#### 2.2.1 架构对比

| 维度 | 传统 1:1 模式 | HOOT 1:N 模式 |
|------|-------------|---------------|
| **架构** | 1 用户 = 1 Freqtrade = 1 VPS | 1 Freqtrade = N 用户（共享信号） |
| **100 用户成本** | ~$1,200/月（100 台 VPS） | ~$48/月（1 台高配 VPS） |
| **成本降低** | 基准 | **96%** |
| **运维复杂度** | 管理 100+ 独立服务器 | 管理 1 台中央引擎 |
| **信号一致性** | 各自独立运行，信号可能不一致 | 统一信号源，所有用户同步 |
| **用户扩展** | 线性增长成本 | 近零边际成本 |
| **故障影响** | 单点故障仅影响 1 用户 | 需高可用保障 |
| **策略更新** | 需逐台更新 | 一次更新，全局生效 |

#### 2.2.2 信号链路详解

HOOT 的信号从生成到执行，经过以下完整链路：

```
信号链路全流程:

Step 1: 信号生成
┌──────────────────────────┐
│  Freqtrade (dry_run=true)│
│  运行量化策略             │
│  检测到买入/卖出信号      │
│  触发 Webhook POST       │
└──────────┬───────────────┘
           │ HTTP POST (HMAC-SHA256 签名)
           ▼
Step 2: 信号接收与验证
┌──────────────────────────┐
│  NestJS SignalsService   │
│  验证 HMAC 签名          │
│  解析信号数据             │
│  写入 signals 表         │
│  推送到 BullMQ signal 队列│
└──────────┬───────────────┘
           │
           ▼
Step 3: 信号分发（按订阅隔离）
┌──────────────────────────┐
│  SignalProcessor         │
│  查询所有活跃订阅         │
│  按 subscriptionId 分发  │
│  每个订阅 = 1 个 trade 任务│
│  推送到 BullMQ trade 队列 │
└──────────┬───────────────┘
           │ N 个独立任务
           ▼
Step 4: 交易执行
┌──────────────────────────┐
│  TradeProcessor          │
│  获取用户交易所 API Key   │
│  内存解密 (AES-256-GCM)  │
│  执行风控检查 (8 大机制)  │
│  通过 CCXT 下单           │
│  记录执行日志             │
│  推送通知给用户            │
└──────────┬───────────────┘
           │
           ▼
Step 5: 交易所执行
┌──────────────────────────┐
│  Binance / OKX / Bybit   │
│  在用户自己的账户上成交    │
│  返回订单信息             │
└──────────────────────────┘
```

**关键设计点：**

| 设计 | 说明 |
|------|------|
| **Freqtrade dry_run=true** | Freqtrade 仅运行策略逻辑生成买卖信号，不实际交易。HOOT 后端负责在用户的交易所账户上实盘交易 |
| **HMAC-SHA256 签名** | Webhook 请求携带 HMAC 签名，防止伪造信号注入 |
| **subscriptionId 隔离** | 每个用户-策略订阅拥有唯一 subscriptionId，信号分发和持仓管理都按此隔离，确保多策略互不干扰 |
| **BullMQ 双队列** | signal 队列负责信号分发，trade 队列负责交易执行。两级解耦，互不阻塞 |
| **重试机制** | 交易执行失败自动重试 3 次，指数退避间隔（1s, 2s, 4s） |
| **全链路追溯** | 从信号生成到交易执行，全程记录 signalId, executionId, orderId，支持审计 |

#### 2.2.3 多订阅隔离机制

传统跟单系统通常按用户维度管理持仓，当一个用户同时订阅多个策略时，容易出现持仓混乱。HOOT 采用 **subscriptionId 级别隔离**：

```
用户 A 同时订阅了 3 个策略:

┌────────────────────────────────────────────────┐
│ 用户 A                                          │
│                                                  │
│  订阅 1 (sub_001) ─── 策略: BTC 突破             │
│  │  持仓: BTC/USDT Long                         │
│  │  风控: 止损 -5%, 止盈 +10%                    │
│  │                                               │
│  订阅 2 (sub_002) ─── 策略: ETH 均值回归          │
│  │  持仓: ETH/USDT Short                        │
│  │  风控: 止损 -3%, 止盈 +8%                     │
│  │                                               │
│  订阅 3 (sub_003) ─── 策略: 多币种网格            │
│  │  持仓: SOL/USDT Long, DOGE/USDT Long         │
│  │  风控: 全局止损 -10%                          │
│                                                  │
└────────────────────────────────────────────────┘

每个订阅的信号分发、持仓管理、盈亏计算、燃油费结算
都按 subscriptionId 独立隔离，互不干扰。
```

### 2.3 安全架构

HOOT 在安全设计上遵循"**纵深防御**"原则，从认证、加密、传输、存储到审计，构建多层安全体系。

#### 2.3.1 API Key 加密存储

用户的交易所 API Key 是最敏感的数据，HOOT 采用 **AES-256-GCM** 认证加密方案：

| 安全措施 | 实现方式 |
|---------|---------|
| **加密算法** | AES-256-GCM（认证加密，同时提供保密性与完整性） |
| **存储字段** | `encrypted_blob` + `iv`（初始向量） + `auth_tag`（认证标签） |
| **密钥管理** | 加密密钥通过环境变量注入 Docker 容器，不写入代码或配置文件 |
| **IV 随机化** | 每次加密生成 12 字节随机 IV，防止密文重放攻击 |
| **使用策略** | 仅在执行交易时解密到内存，交易完成后立即销毁明文 |
| **权限分离** | API Key 存储与交易执行在不同服务层，互相隔离 |
| **物理隔离** | 明文 API Key 永不落盘、永不写入日志 |

```
加密流程:
  用户输入 API Key → AES-256-GCM 加密 → 存储 (encrypted_blob + iv + auth_tag)
                                          ↓
  交易执行时 → 内存解密 → CCXT 下单 → 销毁明文
```

#### 2.3.2 认证体系

HOOT 支持 **三种认证方式**，覆盖 Web、移动端、Telegram 等全场景：

| 认证方式 | 技术实现 | 适用场景 |
|---------|---------|---------|
| **邮箱 + 密码** | JWT (RS256) + bcrypt 哈希 | Web 端标准登录 |
| **Web3 钱包签名** | ethers.js `verifyMessage` + MetaMask | DApp 用户登录 |
| **Telegram Mini App** | Bot Token 验证 + WebApp initData 校验 | Telegram 生态用户 |
| **管理员 2FA** | TOTP (RFC 6238) + speakeasy | 管理后台敏感操作 |

**JWT 安全策略：**
- 访问令牌有效期 15 分钟
- 刷新令牌有效期 7 天
- 敏感操作（提现、修改 API Key）需二次验证

#### 2.3.3 资金精度保障

在加密货币交易中，资金精度直接关系到用户的利益。JavaScript 原生 `Number` 类型存在浮点数精度问题（如 `0.1 + 0.2 !== 0.3`），在资金计算场景中可能导致严重错误。

HOOT **全平台强制使用 Decimal 精度**：

| 层级 | 实现 | 说明 |
|------|------|------|
| **数据库** | `DECIMAL(18,8)` | PostgreSQL 原生精确类型，小数点后 8 位 |
| **ORM** | Prisma `Decimal` | 自动映射，类型安全 |
| **计算** | `decimal.js` | 所有四则运算使用精确计算库 |
| **传输** | 字符串格式 | 前后端 JSON 传输使用字符串，避免精度丢失 |
| **幂等性** | `uniqueOrderId` | 所有计费操作使用唯一订单号 + 数据库唯一约束，杜绝重复扣费 |

**幂等性设计：**

```
uniqueOrderId 格式: {type}_{userId}_{timestamp}_{nonce}
示例: subscription_user123_1706745600_abc123

数据库唯一约束确保：即使因网络重试导致多次请求，也只会执行一次扣费。
```

### 2.4 风控系统

HOOT 内置 **8 大风控机制**，从单笔交易到全局账户，构建多层次风险防护体系。所有风控逻辑在交易执行前后自动运行，无需用户手动干预。

#### 8 大风控机制详细说明

| # | 机制名称 | 触发条件 | 监控周期 | 执行动作 | 状态 |
|---|---------|---------|---------|---------|------|
| 1 | **止盈止损** | 持仓盈亏达到用户设定的阈值 | 5 秒轮询 | 自动平仓，锁定收益或止损 | ✅ 已实现 |
| 2 | **追踪止损（Trailing Stop）** | 价格创新高后回落超过设定比例 | 5 秒轮询 | 动态调整止损线，保护浮盈 | ✅ 已实现 |
| 3 | **最大持仓限制** | 单币种或全局持仓数超过上限 | 开仓前检查 | 拒绝新开仓，防止过度暴露 | ✅ 已实现 |
| 4 | **同币种检查** | 已有同一币种持仓 | 开仓前检查 | 拒绝重复开仓，避免仓位重叠 | ✅ 已实现 |
| 5 | **日亏损限制** | 当日累计亏损超过设定金额/比例 | 每笔平仓后 | 暂停当日所有交易，次日自动重置 | ✅ 已实现 |
| 6 | **黑天鹅保护** | 单笔持仓亏损超过 10% | 10 秒监控，5 分钟滑动窗口 | 强制平仓，触发告警通知 | ✅ 已实现 |
| 7 | **瀑布保护 / DCA 降仓** | 连续亏损或短时间内大幅下跌 | 连续亏损计数 | 逐步降低仓位比例，减少风险暴露 | ✅ 已实现 |
| 8 | **熔断机制（Circuit Breaker）** | 触发条件可配，或用户手动 Kill Switch | 三态自动机 | 平仓所有持仓，暂停所有策略 | ✅ 已实现 |

#### 熔断器三态自动机

熔断器采用经典的三态设计，参考 Netflix Hystrix 模式：

```
正常状态 (CLOSED)
  │
  │ 连续失败/亏损达到阈值
  ▼
熔断状态 (OPEN) ───── 所有交易请求被拒绝
  │                    冷却时间: 30 分钟
  │ 冷却时间到达
  ▼
半开状态 (HALF_OPEN) ── 允许少量试探交易
  │
  ├── 试探成功 → 回到 CLOSED (正常)
  │
  └── 试探失败 → 回到 OPEN (继续熔断)
```

## 5. 商业模式

### 5.1 收入来源

HOOT 平台采用多元化收入模型，确保平台可持续发展的同时，保持对用户友好的定价策略。

| 收入类型 | 机制 | 预估比例 | 说明 |
|---------|------|---------|------|
| **燃油费（Gas Fee）** | 盈利交易抽取 20%，平台从中抽 30%（净收 6%） | ~60% | 仅在用户盈利时收费，与用户利益一致 |
| **会员订阅费** | $15/月、$36/季、$99/年 | ~25% | 提供高级功能与专属策略 |
| **策略授权费** | 第三方策略上架分成 30% | ~10% | 打造策略生态，激励优质策略开发者 |
| **其他费用** | 提现手续费 0.1%，数据服务费 | ~5% | 覆盖链上交易成本与基础设施费用 |

**收入机制特点：**

1. **盈利共享模式**：燃油费机制确保平台与用户利益深度绑定——用户不盈利，平台不收费
2. **低门槛进入**：基础功能免费使用，用户可先验证平台价值再决定升级会员
3. **透明计费**：所有费用明码标价，用户可在任何时间查看详细账单
4. **无隐藏费用**：不收取账户管理费、数据费或平台使用费

### 5.2 成本结构

HOOT 平台致力于保持精益运营，将更多资源投入产品研发与用户体验优化。

| 成本类目 | 说明 | 占比 |
|---------|------|------|
| **基础设施** | DigitalOcean VPS、PostgreSQL、Redis、S3 存储 | ~25% |
| **区块链费用** | BSC Gas 费用（极低）、节点服务 | ~5% |
| **第三方服务** | DeepL API（10 语言翻译）、通知服务、监控告警 | ~10% |
| **安全与合规** | SSL 证书、加密服务、安全审计、KYC/AML | ~15% |
| **研发团队** | 核心开发、量化研究、产品设计 | ~35% |
| **运营推广** | 市场营销、社区运营、客户支持 | ~10% |

**成本优化策略：**

- **容器化部署**：使用 Docker 实现快速扩展，按需分配资源
- **数据库优化**：采用 PostgreSQL + Redis 双层架构，减少冗余查询

- **代码复用**：Monorepo 架构，前后端共享类型定义与工具函数
- **自动化运维**：通过脚本与监控系统减少人工干预

## 8. 风险披露

**重要提示：请在使用 HOOT 平台前仔细阅读本风险披露部分。加密货币量化交易存在高风险，您可能损失全部投资本金。**

### 8.1 市场风险

#### 8.1.1 价格波动风险
- **加密货币市场波动剧烈**：比特币、以太坊等主流币种日内波动可达 10% 以上，山寨币波动更大
- **流动性风险**：部分币种在极端行情下可能出现流动性枯竭，导致无法按预期价格成交
- **黑天鹅事件**：如 Luna 崩盘、FTX 倒闭等事件，可能导致市场急剧下跌

**HOOT 的应对措施：**
- 8 大风控机制（止损、熔断、黑天鹅保护）
- 仅交易主流币种（BTC、ETH、BNB 等）
- 最大持仓限制，避免过度集中

#### 8.1.2 历史收益不代表未来表现
- **策略失效风险**：历史表现优秀的策略可能在市场环境变化后失效
- **过拟合风险**：部分策略可能针对历史数据优化，但在实盘中表现不佳
- **市场周期**：牛市与熊市策略表现可能截然不同

**用户应注意：**
- 回测收益仅供参考，实盘收益可能显著不同
- 定期评估策略表现，及时调整或停止不佳策略
- 分散投资多个策略，降低单一策略失效风险

### 8.2 技术风险

#### 8.2.1 交易所风险
- **API 中断**：交易所 API 可能因维护、攻击、故障等原因中断，导致无法下单或查询持仓
- **限流与封禁**：过于频繁的 API 调用可能导致被限流甚至封禁账户
- **交易所倒闭**：如 FTX 事件，交易所倒闭可能导致资金无法取回

**HOOT 的应对措施：**
- 使用 CCXT 库统一处理 API 异常，自动重试
- 速率限制器，避免触发交易所限流
- 建议用户不要在交易所存放过多资金，交易完成后及时提现到链上钱包

#### 8.2.2 网络延迟与滑点
- **延迟风险**：VPS 到交易所的网络延迟可能导致错过最佳成交价格
- **滑点**：市场波动剧烈时，实际成交价可能偏离预期价格

**HOOT 的应对措施：**
- VPS 部署在与交易所同机房或同地区，延迟低至 10ms 以内
- 使用限价单而非市价单，控制滑点

#### 8.2.3 智能合约风险
- **代码漏洞**：智能合约可能存在未发现的漏洞，导致资金损失
- **升级风险**：合约升级可能引入新的风险

**HOOT 的应对措施：**
- 智能合约将由 CertiK 或 SlowMist 审计（计划 Q2 2026）
- 采用可升级合约架构，但升级需通过 DAO 投票
- 代码开源，接受社区审计

### 8.3 监管风险

#### 8.3.1 政策不确定性
- **各国监管差异**：美国、欧盟、中国、日本等国对加密货币的监管政策不同且可能变化
- **证券认定风险**：HOOT 代币可能被某些国家认定为证券，需要注册或停止服务
- **税务合规**：用户需自行遵守所在国税务法规，HOOT 不提供税务建议

**HOOT 的应对措施：**
- 持续关注全球监管动态，及时调整合规策略
- 在合规明确的地区优先开展业务（如瑞士、新加坡）
- 与法律顾问合作，确保符合适用法规

#### 8.3.2 交易所监管
- **KYC/AML 要求**：交易所可能要求用户完成身份验证，HOOT 无法代替用户完成
- **地域限制**：部分交易所不向特定国家用户提供服务（如美国）

**用户应注意：**
- 确保使用的交易所在您所在地区合法合规
- 遵守交易所的 KYC/AML 要求

### 8.4 操作风险

#### 8.4.1 用户操作失误
- **API Key 泄露**：如 API Key 泄露，他人可能操作您的交易所账户
- **错误配置**：不当的风控配置（如止损设置过宽）可能导致超预期亏损
- **杠杆风险**：使用高杠杆（如 10x、20x）可能导致快速爆仓

**HOOT 的应对措施：**
- API Key 使用 AES-256-GCM 加密存储，仅在交易时解密
- 强制要求用户设置止损止盈，避免无限亏损
- 默认禁用杠杆，用户需手动开启并确认风险提示

**用户应注意：**
- 妥善保管 API Key，定期轮换，设置 IP 白名单
- 不要授予 API Key 提现权限（HOOT 不需要）
- 从小额资金开始，逐步增加投入
- 充分理解策略逻辑后再使用，不盲目跟单

#### 8.4.2 账户安全
- **密码泄露**：如 HOOT 账户密码泄露，可能导致资金被盗
- **钓鱼攻击**：仿冒 HOOT 网站可能诱导用户输入敏感信息

**HOOT 的应对措施：**
- 强制启用双因素认证（2FA）
- 异常登录检测（新设备、异常 IP）
- 敏感操作（提现、修改 API Key）需邮件确认

**用户应注意：**
- 使用强密码，启用 2FA
- 通过官方渠道访问 HOOT（收藏官网链接）
- 警惕钓鱼邮件与短信

HOOT 平台内置 **8 大风控机制**，最大程度保护用户资金安全：

#### B.3 API Key 加密方案

```typescript
// 加密算法：AES-256-GCM
// 密钥管理：环境变量注入，不落盘
// 存储字段：encrypted_blob + iv + auth_tag

// 加密流程
const crypto = require('crypto');
const algorithm = 'aes-256-gcm';
const key = Buffer.from(process.env.ENCRYPTION_KEY, 'hex'); // 32 字节

function encrypt(plaintext: string) {
  const iv = crypto.randomBytes(12); // GCM 推荐 12 字节 IV
  const cipher = crypto.createCipheriv(algorithm, key, iv);

  let encrypted = cipher.update(plaintext, 'utf8', 'base64');
  encrypted += cipher.final('base64');

  const authTag = cipher.getAuthTag();

  return {
    encrypted_blob: encrypted,
    iv: iv.toString('base64'),
    auth_tag: authTag.toString('base64'),
  };
}

// 解密流程
function decrypt(encrypted_blob: string, iv: string, auth_tag: string) {
  const decipher = crypto.createDecipheriv(
    algorithm,
    key,
    Buffer.from(iv, 'base64')
  );

  decipher.setAuthTag(Buffer.from(auth_tag, 'base64'));

  let decrypted = decipher.update(encrypted_blob, 'base64', 'utf8');
  decrypted += decipher.final('utf8');

  return decrypted;
}
```

**安全特性：**
- **认证加密（AEAD）**：GCM 模式同时提供保密性与完整性
- **密钥管理**：密钥仅在 Docker 启动时通过环境变量注入，不写入代码或配置文件
- **IV 随机化**：每次加密生成新的 IV，防止密文重放攻击
- **权限分离**：API Key 仅在执行交易时解密到内存，用完立即销毁
