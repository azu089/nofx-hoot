## 1. 协作核心原则

### 1.1 决策权划分

| 决策类型 | 负责方 | 说明 |
|---------|-------|------|
| 功能需求 | PM | 做什么、不做什么、验收标准 |
| 技术实现 | AI | 怎么做、用什么库、代码怎么写 |
| 架构选型 | PM + AI | AI 提供方案，PM 最终决策 |
| Bug 修复 | AI | AI 负责定位和修复，PM 负责验收 |

**核心规则：**
- PM 只做「通过/打回」，不写代码
- AI 提供完整实现，不做口头承诺
- 有歧义时 AI 先提供 2-3 种方案，PM 选择后再实现

### 1.2 验收标准（Definition of Done）

一次交付完成，必须同时满足：

1. **可用能力**: 本轮只交付 1 个原子任务
2. **肉眼可见成功信号**: 必须能用 curl/Postman/页面 证明功能已生效
3. **验收步骤**: 提供明确的执行步骤 + 预期结果
4. **回滚方案**: 明确如何撤销本次改动
5. **风险与影响说明**: 说明潜在风险点、影响范围

## 3. 风险分级与审批

| 风险等级 | 操作类型 | 审批要求 |
|---------|---------|---------|
| **高风险** | 删表、改架构、修改鉴权 | 必须 PM 明确批准 |
| **中风险** | 新增依赖、改接口签名 | 需 PM 确认后执行 |
| **低风险** | 新增接口、修 Bug | 正常流程，告知即可 |

### 高风险操作清单

以下操作**必须等 PM 明确说"可以"后才能执行**：

- 删除任何文件或目录
- 修改 `.env` / `docker-compose.yml`
- 引入新的 npm 依赖
- 修改数据库 schema
- 修改用户鉴权/授权逻辑
- 执行 `git push`
- 修改 CI/CD 配置

## 4. QuantFi 业务特殊规则

### 4.1 资金安全

- 所有金额使用 `DECIMAL(18,8)`
- 禁止使用 `FLOAT` 或 `DOUBLE`
- 计费必须幂等（unique_order_id）
- 涉及资金操作必须提供验算脚本

### 4.2 API Key 安全

- 必须 AES-256-GCM 加密存储
- 字段：`encrypted_blob` + `iv` + `auth_tag`
- 严禁日志输出明文
- 仅在容器启动时注入内存环境变量

### 4.3 单租户隔离

- 每个 VIP 用户 = 1 独立 VPS
- 心跳检测：15 分钟无心跳 = 僵尸节点
- 销毁前必须备份到 S3
- 销毁后必须退款

### 4.4 双轨质押

- A 类（空投/积分）：提前解押扣 50% 本金
- B 类（本金购买）：提前解押扣收益 + 3% 手续费
- 权重：A 类固定 1.0x，B 类 1.0x-3.0x 递增

### 第一部分：核心逻辑理清（修正开发方式）

你之前的误区在于：**过度依赖 AI 的“代码生成能力”，忽视了 AI 的“产品把控能力”不足。**
AI 擅长写逻辑，不擅长审美和系统健壮性。

**正确的开发/修正逻辑应该如下（V型修正模型）：**

1. **停止 (Stop)**：停止所有新功能开发（Web3、App、新策略全部暂停）。
2. **定义 (Define)**：重新定义“V1 上线标准”。
* **UI 标准**：必须达到竞品（如 Pionex/Binance）的 80% 美观度。
* **功能标准**：核心资金链路（充值->跑策略->提现）必须 0 报错。


3. **修复 (Fix)**：
* **UI 优先**：先修整皮囊，皮囊好看了，你才有心情测功能。
* **QA 跟进**：按剧本测试，修复核心 Bug。


4. **验证 (Verify)**：
* **实盘测试**：你自己充钱跑通全流程。


5. **发布 (Release)**：
* 部署上线，开放给首批用户。

### 第二部分：QuantFi 项目落地执行方案 (Action Plan)

请按照以下 **3 个阶段** 严格执行。每个阶段不完成，**严禁**进入下一阶段。

#### 阶段一：UI 重构与视觉升级 (耗时：2-3 天)

**目标**：消除“廉价感”，让产品看起来像一个正经的商业 SaaS。

**执行步骤：**

1. **准备参考图 (Reference)**：
* 去截图 **Binance (Pro版)** 或 **Pionex (派网)** 的以下页面：
* 首页/Dashboard（资产展示、收益曲线）。
* 策略列表页（卡片样式、收益率颜色）。
* 钱包页（充值/提现表单）。


* *如果没有现成图，使用 v0.dev 生成一张“Dark Mode Crypto Dashboard”的图。*


2. **单页精修 (Page-by-Page Polish)**：
* 打开 Claude Code / Cursor。
* **指令词**（请直接使用）：
> “我现在要修正 QuantFi 的 UI。请遵循以下原则：


> 1. **参考风格**：暗黑模式 (Background: #0B0E11)，主色调使用科技蓝 (#3772FF)，涨绿跌红。
> 2. **组件规范**：使用 Shadcn UI + Tailwind CSS。所有卡片必须有圆角 (rounded-xl) 和微弱的边框 (border-white/10)。
> 3. **任务**：请读取 `/dashboard` 页面的代码，并参考我上传的截图（或描述），重写该页面的 UI 代码。重点优化：资产数字的字体大小（要大）、图表的高度、以及‘启动’按钮的质感。”
> 
> 


* **验收标准**：修改完一个页面，立刻在浏览器看。如果不满意，继续用自然语言调整（“按钮太扁了，加高一点”、“文字颜色太暗了，亮一点”）。
* **复制推广**：Dashboard 修好后，让 AI 把这套 CSS 规范应用到其他页面。


3. **微交互补全 (Micro-Interactions)**：
* **指令词**：
> “检查当前页面的所有按钮和表单。请添加以下交互效果：
> 1. **Hover**：鼠标悬停时按钮变亮。
> 2. **Loading**：点击‘充值’、‘启动’等异步按钮时，按钮必须变灰并显示‘加载中...’转圈动画，防止用户重复点击。
> 3. **Empty State**：如果列表没数据，显示一个‘暂无数据’的图标和提示文案，不要留白。”
> 
> 





#### 阶段二：功能健壮性修复 (耗时：2-3 天)

**目标**：消除报错，确保流程跑通。

**执行步骤：**

1. **控制台清零 (Console Zero)**：
* 打开浏览器开发者工具 (F12) -> Console。
* 操作一遍核心流程。
* **指令词**：
> “我操作了一遍流程，Console 里报了以下错误（复制错误信息）。请分析根源并修复它们。不要只是 try-catch 屏蔽错误，要解决逻辑问题。”




2. **核心链路剧本测试 (Scenario Testing)**：
* **剧本 A：新用户流程**
* 注册 -> 自动跳转 -> 钱包 0 余额 -> 页面不报错。


* **剧本 B：资金流程**
* 充值（模拟或真实） -> 余额增加 -> 状态变更为“成功”。


* **剧本 C：策略流程**
* 余额不足时点击启动 -> **必须弹窗提示“余额不足”**（而不是没反应或报错）。
* 余额充足点击启动 -> 状态变“运行中” -> VPS 成功创建。


* **指令词**：
> “我正在测试 [场景名称]。我期望发生 [X]，但实际发生了 [Y]。请修复这个逻辑漏洞。”





#### 阶段三：实盘灰度测试 (耗时：3-5 天)

**目标**：验证真金白银的安全性。

**执行步骤：**

1. **环境准备**：
* 确保 `.env` 配置的是 **真实** 的 DigitalOcean Token 和 **真实** 的 Binance API（只读权限）。
* 数据库使用生产环境数据库（Supabase 或服务器上的 PostgreSQL）。


2. **CEO 实测 (Dogfooding)**：
* 你自己充值 **50 USDT**。
* 真实启动一个策略。
* 观察 24 小时：
* 钱有没有少？（燃油费扣没扣？）
* 单有没有开？
* VPS 有没有自动销毁？（省成本的关键）

### 第三部分：通用版 AI 项目修正规则 (Launch Protocol)

为了让你未来的项目（以及 QuantFi 的后续迭代）不再重蹈覆辙，我为你总结了一套**“Claude Code 修正专用规则”**。

请将以下内容保存为 `FIX_PROTOCOL.md`，每次修整项目时，先发给 Claude Code。

```markdown
# FIX_PROTOCOL.md - AI 项目紧急修正协议

## 1. 核心原则 (Core Principles)
* **视觉优先 (Visual First)**：在功能逻辑跑通之前，先确保界面看起来是“对”的。UI 结构往往决定了数据结构。
* **停止增量 (Stop Scope Creep)**：在修复阶段，**严禁**添加任何 PRD 之外的新功能（如“顺便加个 AI 预测”）。
* **防御性编程 (Defensive Coding)**：假设 API 会失败，假设用户会断网。必须处理 Loading 和 Error 状态。

## 2. 修正工作流 (Workflow)

### 步骤 A：UI 诊断与重构
* **输入**：核心页面代码 + 竞品截图/设计描述。
* **动作**：
    1.  统一色调与字体（建立 `tailwind.config.js` 主题）。
    2.  标准化组件（Button, Card, Input）。
    3.  **强制要求**：所有异步操作必须加 Loading 状态；空数据必须加 Empty State。
* **验收**：截图对比，达到 80% 相似度。

### 步骤 B：报错清洗 (Bug Bash)
* **输入**：浏览器 Console 报错日志 + 后端 Terminal 报错日志。
* **动作**：
    1.  一次性修复所有红色 Error。
    2.  检查 API 接口的 Return Type，确保前后端类型一致（TypeScript 优势）。
    3.  检查环境变量 (`.env`) 是否遗漏。

### 步骤 C：链路验证 (Critical Path)
* **输入**：测试剧本（用户从注册到付费的全流程）。
* **动作**：
    1.  模拟用户操作，记录卡顿/报错点。
    2.  修复阻塞性 Bug (P0)。
    3.  **验证数据一致性**：前端显示的余额 = 数据库存的余额。

## 3. 给 AI 的指令模板 (Prompt Templates)

* **修 UI**：“@DashboardPage 请参考 [暗黑模式/竞品风格]，重构本页面的 CSS。要求：卡片圆角 16px，阴影柔和，字体层级分明。添加 Loading 和 Error 状态处理。”
* **修 Bug**：“@ConsoleLog 我在执行 [操作] 时遇到了这个错误。请分析是前端参数传错了，还是后端逻辑问题？请修复并给出解释。”
* **查漏补缺**：“请扫描当前项目，列出所有还在使用 Mock 数据（假数据）的地方，并帮我替换为真实的 API 调用。”

```
