# 开发工作流规则（强制执行）

---

## !!!!! 修改前必须全局理解（最高优先级，不可跳过）!!!!!

**修改任何逻辑之前，必须按顺序完成以下三步，禁止靠猜：**

### Step 1：读完整相关代码
- 找到涉及该功能的**所有**相关文件，完整阅读，不能只看报错行或片段
- 如果是网格/交易逻辑，必须先读 `reference/nofx/` 对应实现（见 nofx参考规则.md）
- 禁止"看到一个函数就改"，必须理解整个调用链

### Step 2：全局评估，输出结论
修改前必须输出：
```
## 修改前评估

### 相关代码已读
- [文件路径:行号] — [读到的关键逻辑]

### 根本原因
[为什么会有这个问题，不是表象，是根源]

### 影响范围
[这处改动会影响哪些调用方/功能]

### 与 nofx 的对比（涉及网格/交易时必填）
[nofx 怎么做的，HOOT 当前怎么做的，差异是什么]

### 修改方案
[最小改动方案，以及为什么选这个而不是其他]
```

### Step 3：等确认后再执行
- 输出评估后，**等 PM 确认**再写代码
- 如果 PM 说"你评估"/"你看"，输出评估结论，不要直接改代码

**违反以上规则 = 交付不合格，必须打回。**

历史教训（本项目已发生）：
- 只看 capUsed 偏高就改 pendingNotional 计算方式，未读 nofx 实现，导致反复修改
- 看到 AI 只挂 2 格就加"必须补全所有空层"规则，未追查根本原因（实为 capUsedPct 虚高）
- 每次修复都向 prompt 添加规则，最终积累大量过度约束，干扰 AI 判断

## 6 段固定结构（每轮必须输出）

1. **本轮任务理解（≤5行）** - 只做什么 / 不做什么
2. **变更计划 & 文件列表** - 白名单 + 禁止项
3. **实现内容（按文件分段）** - 补丁风格说明
4. **验证步骤** - 目录 + 命令 + 预期输出
5. **风险点 & 自检清单** - 影响 + 风险 + 回滚方式
6. **回滚方案** - 具体步骤

---

## 原子任务粒度

一个原子任务 = 一个接口 / 一个脚本 / 一个页面

**禁止同时动：**
- 多个模块（如 wallet + stake + trading）
- 前后端一起大改
- 重构 + 改业务

---

## 反死循环机制

连续 2 轮失败 → 自动进入反死循环模式：

1. **冻结范围** - 只改一个文件/函数
2. **写清复现步骤** - Given/When/Then
3. **最小修复** - 只改最可能的一个点
4. **最小自测** - 只针对这个点验证

---

## 提交规范

### 小步提交
- 单次提交 ≤ 5 个文件
- 每个变更配：自检清单 + 回滚步骤

### 提交信息格式
```
[类型] 简短描述（≤50字符）

详细说明:
- 改了什么
- 为什么改
- 影响范围
- 如何验证
- 如何回滚
```

类型：
- `[feat]` 新功能
- `[fix]` 修复 bug
- `[docs]` 文档更新
- `[refactor]` 重构
- `[test]` 测试
- `[chore]` 杂项
