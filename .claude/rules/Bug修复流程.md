# Bug 修复工作流规则

## 核心原则

修一个 bug，不能出现更多 bug。

---

## 修复前必做

### 1. 理解问题根源
- 不只看报错，要理解为什么
- 重现问题的步骤是什么
- 什么时候开始出现的

### 2. 分析影响范围
- 这个模块被谁调用？
- 改了这里，还有哪里会受影响？
- 是否涉及资金/权限等敏感操作？

### 3. 检查相关代码
- 读取相关文件，理解整体逻辑
- 查看 git log 最近的改动
- 确认是代码问题还是配置问题

### 4. 制定最小修复
- 改动越少，风险越小
- 不要顺手重构
- 不要顺手加功能

---

## 修复后验证

- [ ] 原问题解决了
- [ ] 相关功能没坏
- [ ] 编译无报错
- [ ] 单元测试通过

---

## 禁止行为

- 看到报错就直接改
- 复制网上方案不理解
- 顺手重构
- 改了不测试

---

## 报错处理模板

PM 回传报错后，AI 必须按此结构输出：

```
## 1. 报错含义（大白话）
[1-2 句解释这个错误是什么意思]

## 2. 最可能的 3 个原因（按概率排序）
1. [原因1] - 概率最高
2. [原因2]
3. [原因3]

## 3. 每个原因的检查步骤

### 检查原因1
- 命令：`xxx`
- 执行目录：`xxx`
- 预期输出：`xxx`
- 如果不对：[下一步]

### 检查原因2
...

## 4. 最小修复方案
- 修改：[具体文件和内容]
- 复测命令：`xxx`
- 预期结果：`xxx`
```
