# PM 工作流规则

## 核心原则

PM 只做两件事：
1. **输入需求** - 用中文描述想要什么
2. **看网页验收** - 确认功能是否正确

AI 做所有其他事情。

---

## 绝对不能让 PM 做

- 运行命令
- 启动服务
- 修复报错
- 安装依赖
- 查看日志
- 改配置文件

---

## 验收前检查清单

AI 必须在告诉 PM 验收前完成：

- [ ] Docker 服务运行中
- [ ] 后端 API 可访问
- [ ] 前端页面可打开
- [ ] 代码无编译错误
- [ ] 功能真的可见（不是占位符）

---

## 输出格式

```
## 任务完成

### 做了什么
- [改动1]
- [改动2]

### 已验证
- 服务运行中
- 代码无报错
- 接口可访问

### 验收方式
打开网页：http://localhost:xxx
应该看到：[描述]
```

---

## PM 验收清单

PM 只需要按以下判断 **通过 / 打回**：

| 检查项 | 说明 |
|-------|------|
| 3 分钟内走通流程 | 接口/脚本/页面能正常运行 |
| 权限正确 | 不越权、不泄露敏感信息 |
| 数据真实生效 | 写入后刷新/重启仍存在 |
| 异常态齐全 | 空数据/失败/超时有清晰提示 |
| 日志可定位 | 出错能看到 request_id |
| 可回滚 | 给了明确回滚步骤 |

---

## 通过（Pass）的最低条件

必须**全部满足**：

1. 你能在 3 分钟内按"验收步骤"走通并看到成功信号
2. 异常态/边界态至少覆盖 1 个（不是只会成功）
3. 日志能定位（有 request_id / 有关键上下文）
4. 有回滚方案（你能照着做回退）
5. 文档已同步（如果动了配置/依赖/启动方式）

---

## 打回（Fail）的任一条件

只要满足以下**任意一条**，必须打回：

| # | 打回条件 |
|---|---------|
| 1 | 没有计划就给代码 |
| 2 | 只说"运行一下"不说目录与成功信号 |
| 3 | 越权改了禁止项/白名单外文件 |
| 4 | 没有回滚方案 |
| 5 | 不提供验收步骤或步骤不可执行 |
| 6 | 配置/依赖变更不写入 README/DEV_Log |
| 7 | 连续修复失败但不启用"反死循环机制" |
| 8 | DoD 6 条硬标准任一不满足 |

---

## PM 回传信息模板（排错专用）

当出现报错时，PM 回传以下信息：

```
## 我做了什么
1. [操作步骤1]
2. [操作步骤2]
3. [操作步骤3]

## 预期结果
[应该看到什么]

## 实际结果
[实际看到什么 - 截图/日志/响应]

## 完整报错
[完整报错文本，不要截断]

## 环境信息
- OS: macOS/Windows/Linux + 版本
- Node: v20.x
- pnpm: 9.x
- Docker: 是/否 + 版本
- 代理/镜像: 是/否
```

AI 收到后必须按《Bug修复流程.md》的报错翻译模板输出。

---

## PM 快速下达任务模板

```
【阶段标记】例如：Phase1-Task1.1 数据库设计

【本轮只做什么】
- 2-3 行，必须可验收

【本轮不做什么】
- 明确禁止项（不动哪些模块/文件/接口）

【验收方式】
- 3-5 条固定命令/步骤 + 预期结果

【回滚要求】
- 必须可回退到上一个稳定版本

【环境信息】（如涉及运行）
- OS/运行时版本/包管理器/Docker/代理
```
